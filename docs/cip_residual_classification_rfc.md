## 2. Bucket taxonomy and precedence (applied identically to both engines)

Every mismatching `(smiles, atom_idx)` is passed through one deterministic
pipeline, first-match-wins:

| # | Bucket | Trigger |
|---|---|---|
| 1 | `pseudoasymmetric` | oracle (`modern`, `rdCIPLabeler`) label at this atom is lowercase `r`/`s` |
| 2 | `aromaticity_kekulize_bug` | `chematic_core::kekulize()` hard-fails on this molecule, **and** the failing atom is the stereocenter itself, a direct neighbor, or shares an SSSR ring with a direct neighbor (§3's locality gate) |
| 3 | `phosphorus` | the stereocenter atom itself is P |
| 4 | `aromaticity_other` | the stereocenter has ≥1 direct aromatic neighbor, not already caught by #2 |
| 5 | `multiple_bond_dup` | a direct, non-aromatic neighbor of the stereocenter itself carries a double/triple bond to a third atom (the classic CIP phantom-duplication trigger point) |
| 6 | `rule4b_candidate` | the stereocenter's neighbors contain a constitutionally-tied pair (equal RDKit canonical rank with chirality excluded — i.e. Rules 1a/2 alone cannot separate them) **and** ≥1 embedded chiral atom exists elsewhere in the molecule |
| 7 | `rule3_candidate` | same tied-pair precondition as #6, but the discriminating structural feature is a stereo-specified (E/Z) double bond elsewhere instead of an embedded chiral atom |
| 8 | `rule5_candidate` | same tied-pair precondition, uppercase oracle label, no #6/#7 signal — the only rule left that could break a genuine Rules-1a/2 tie |
| 9 | `unclassified` | none of the above fired |

**Why Rule 4a/4c never appear as a separate bucket.** `docs/cip_accurate_rfc.md`
Milestone 4B-0 already established this directly, not per-row: `chematic_core::
Chirality` has exactly one non-`None` variant family (tetrahedral
`CounterClockwise`/`Clockwise`) — there is no unit-*type* distinction for Rule
4a to compare, and no axial/planar/bond `Chirality` variant for Rule 4c to
compare either. This is a fact about the enum both engines share, true for
every row, not re-derived here — any Rule-4-shaped residual in this
project's current data model is necessarily 4b.

**Why `pseudoasymmetric` and `rule5_candidate` are reported separately** (the
RFC's own Milestone 4A-0/4C table folded both into one `rule5_pseudoasymmetric`
bucket). This round's task brief lists them as distinct categories, so:
`pseudoasymmetric` = the residual atom's *own* oracle descriptor is lowercase
(chematic has no `LowerR`/`LowerS`-capable comparator path reaching it, or —
for the accurate engine — declines rather than guesses); `rule5_candidate` =
an *uppercase*-labeled atom whose only remaining explanation, after ruling out
every other structural mechanism, is that resolving a genuine Rules-1a/2 tie
needed some form of R/S ordinal comparison. On this corpus, for both engines,
`rule5_candidate` measures **0** — every tied-pair case found also has an
embedded chiral atom (routes to `rule4b_candidate`) or nothing else (routes to
`unclassified`, since the tied-pair signal never fires alone in this data).
Flagged explicitly as a **weak, heuristic bucket** — its absence here says
"not observed on this corpus," not "chematic has no Rule-5-shaped bug."

**Locality, not mere co-occurrence, for the kekulize cross-check.** "This
molecule's `kekulize()` fails somewhere" is not evidence that a *specific*
stereocenter's mismatch is caused by it — a large fused polycyclic drug-like
molecule can have an unrelated ring elsewhere. Bucket #2 only fires when the
failing atom is within one bond of the stereocenter or shares a ring with a
direct neighbor.

**One-engine-blind, deliberately.** The same signals and the same precedence
run for both engines — the classifier never asks "which engine is this" before
deciding a bucket. This is what makes the two engines' numbers genuinely
comparable rather than two different rubrics that happen to share bucket
names.

## 3. Aromaticity-kekulize-bug cross-check, run at full-corpus scale

The parallel `diag/aromaticity-rdkit-parity` diagnosis (read via `git show
diag/aromaticity-rdkit-parity:docs/aromaticity_rdkit_parity_rfc.md`, not
checked out, not rebased onto) found `chematic_core::kekulize()` hard-fails
for 6 of its 40 hand-built fixtures — tropylium cation, imidazolium,
pyridinium, pyrylium, tellurophene, phosphole — root-caused to
`atom_must_be_matched`'s charge-blind lone-pair-donor rules (pyridinium/
pyrylium/imidazolium), a missing acceptor-pattern rule for a cationic
empty-p-orbital ring atom (tropylium), a missing Te(52) donor-list entry
(tellurophene), and P being entirely unhandled (phosphole) — and, critically,
that this failure is *invisible* at the atom/bond aromatic-flag level, because
`build_molecule_from_model` only ever promotes a flag to aromatic, never
demotes one when its own model disagrees with a pre-existing (parser-supplied,
unverified) flag.

Rather than pattern-match those exact 6 SMILES against this CIP corpus (which
would miss any *substituted* variant of the same ring classes), this round ran
the real algorithm on all 5,000 corpus molecules
(`crates/chematic-perception/examples/cip_kekulize_probe.rs` →
`validation/results/cip_kekulize_probe.jsonl`):

```
parse_ok:      5000/5000
kekulize_ok:   4999/5000
kekulize_fail: 1/5000  --  Cc1cn2c(=O)c3ncn(COCCO)c3nc2n1C, atom 16 (N)
```

That one failing molecule has **zero** chiral-tagged atoms
(`Chem.ChiralType.CHI_UNSPECIFIED` on every atom, confirmed directly) — it
cannot appear in any CIP residual, by either engine, because it never enters
the stereocenter comparison at all. Joining this probe against both engines'
full 181-row combined residual (`bucket == "aromaticity_kekulize_bug"` in the
precedence table above) confirms this formally: **0/155 legacy, 0/26
accurate.**

**Reading.** This is a real, measured null result, not an assumption — the
6 flagged ring classes are exotic/charged heteroaromatics that this
particular ChEMBL-shaped drug-like corpus (`SMILES.csv`) simply does not
contain, substituted or otherwise. It does not mean the aromaticity bug is
unimportant (that diagnosis's own §1c already traces a real, silent behavior
change for `chematic-depict`'s Kekulé-rendering option and a plausible one for
`assign_cip_accurate_experimental`'s own MANCUDE Kekulé-clone fallback path,
on molecules simply not present here) — only that, on the corpus this CIP
audit was run against, it contributes **0** to the CIP residual specifically.
A future corpus containing a pyridinium/imidazolium-type permanent cation
(plausible for some drug classes, e.g. quaternary heteroaromatic salts) is
exactly the condition under which this bucket would first become non-empty;
the mechanism (`bucket == "aromaticity_kekulize_bug"`, gated on
`cip_kekulize_probe.rs`'s output) is already wired to catch it if it does.

**No declined answer silently dropped.** The raw `corpus_snapshot --candidate`
values behind every row above were inspected directly, not inferred: all 15
pseudoasymmetric rows and 2 of the 11 phosphorus rows are the string
`skip:tied` — the accurate engine's own `SkipReason::Tied`, a declined answer
surfaced as data (matching Milestone 5A's "don't guess" design), counted here
exactly like a wrong label would be, per this round's `classify_row()`
treating `chematic_code != oracle_code` uniformly regardless of whether the
non-match is a wrong value or an explicit skip.

**Reading, restating the RFC's own already-closed gate in this round's
taxonomy:** subtract the 11 oracle-unstable phosphorus rows (not a real
target — there is no reliable ground truth to converge toward) and the
residual is the already-deferred 15-row pseudoasymmetric cage family alone —
**0 unexplained** either way. This round adds nothing new to the accurate
engine's own diagnosis; it exists to show the *same* mechanical classifier
that had to do real, novel work on the legacy engine's residual (§4) produces
the *already-known* answer here, which is itself a form of cross-validation
of the classifier (see §1's byte-identical row-set check).

## Reproduce

```bash
# 1. Kekulize probe (full corpus, ~1s):
cargo run -p chematic-perception --release --example cip_kekulize_probe \
    -- ~/Downloads/SMILES.csv > validation/results/cip_kekulize_probe.jsonl

# 2. Accurate-engine snapshot (~0.5s):
cargo run -p chematic-cip --release --example corpus_snapshot -- \
    --candidate ~/Downloads/SMILES.csv /tmp/accurate_candidate.tsv

# 3. Classification (both engines, ~1-2 min, dominated by RDKit oracle calls):
.venv/bin/python scripts/cip_residual_classification_audit.py \
    --smiles ~/Downloads/SMILES.csv \
    --accurate-tsv /tmp/accurate_candidate.tsv \
    --kekulize-probe validation/results/cip_kekulize_probe.jsonl \
    --oracle-instability validation/cip_oracle_instability.jsonl \
    --out-corpus validation/cip_residual_classification_corpus.jsonl \
    --out-summary validation/results/cip_residual_classification_summary.json
```

`1c47371dcbe37f4e0a141bf545b72bf238de2761fa3894fa251a552d84728d3e`) and RDKit

JSON output; both frozen corpora sorted by `(engine, smiles, atom_idx)`).
